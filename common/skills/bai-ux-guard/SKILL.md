# BAI UX Guard — 情報過多・導線迷子を防ぐUI設計SKILL

## 目的と優先順位

UIの完成条件は「機能を全部表示すること」ではなく「ユーザーが目的の操作を迷わず完了できること」。
ユーザーの明示指示、実際の製品要件、アクセシビリティを優先する。既存の機能やデータを勝手に削除・無効化しない。

## 常時守る設計原則

1. **最初にユーザーの上位3タスクを特定**する。各タスクの開始点、主要操作、完了時のフィードバックを描く。タスク不明なら現行仕様から合理的に仮置きし、仮定として明記する。
2. **画面にはその段階で必要なものを優先表示**する。詳細・高度設定・稀な操作は折り畳み、タブ、詳細ページ、ステップフローに整理する。ただし重要な機能を発見不能にしない。
3. **主行動を明確にする**。主CTAは視覚的に一つ優先。危険操作や対等な主要操作がある場合は例外を説明する。ボタンのテキストは動作を表す具体的な日本語にする。
4. **同じ情報を重複表示しない**。見出し・カード・補足・ツールチップで同文を繰り返さず、ユーザーの判断に必要な情報を残す。
5. **「下にあるから見つからない」を防ぐ**。最初の操作の入口は初期表示領域か明確なナビに置く。長い画面では目次・固定ナビ・検索・絞り込み等を用途に応じて使う。
6. **複雑さを単純に隠蔽しない**。初心者の基本フローを見せつつ、上級者は全機能へ到達可能にする。操作経路は短く、戻る・中止・再試行を備える。
7. **余白・タイポグラフィ・整列による階層を優先**する。大量のカード、枠線、バッジ、色、アイコン、グラデーションを整理手段として乱用しない。
8. **画面密度は役割に合わせる**。ダッシュボード、プロ用編集画面、一覧管理UIでは高密度が適切な場合もある。固定の項目数制限を盲目的に適用せず、根拠を示す。
9. **全機能と導線の対応表を維持**する。仕様の各機能がどの画面から到達できるか、検索可能か、権限・エラー・空状態にどう対応するかを記録する。
10. **未実装の動作を成功したかのように見せない**。HTMLモックでもナビ・ボタン・入力・状態遷移のデモ動作を実装するか、明示的に「デモ／未実装」と表示する。

## 作業フロー

### Phase A: 情報設計（コード前）

- 対象ユーザー、利用状況、上位タスク3件を抽出する。
- 全機能リストを「今必要」「次に必要」「必要時のみ」の3層に分類する。
- 画面ごとの目的と入口／出口を定義し、画面遷移と機能の対応表を作る。
- ユーザーが求めない限り、巨大な1画面に全機能を詰め込まない。

### Phase B: 実装

- 最初に重要な1画面と主要操作フローを作る。
- 画面を増やす場合でも機能を失わず、URL・タブ・パンくず・戻る等で導線をつなぐ。
- 状態を設計する: 初回／空／読み込み／成功／失敗／権限不足／入力エラー。
- 小さい画面、キーボード操作、文字数が長いケースを考慮する。

### Phase C: 出荷前のゲート検査

各項目を PASS / FAIL / NOT TESTED で記録し、FAILを修正する。

- 初見ユーザーが5秒程度で**画面の目的と次の一手**を説明できそうか（仮説。実証にはユーザーテストが必要）
- 主要3タスクを迷わず始められるか、操作が最後までつながっているか
- 画面の上部に操作入口があり、重要操作が無説明の長いスクロールの末尾に隠れていないか
- 高度設定・追加情報が基本フローを圧迫していないか
- 主行動と副行動の視覚的優先度が明確か
- 似た概念、重複したラベル、冗長説明、装飾カードの乱立がないか
- 空、読み込み、成功、失敗などの状態に復帰導線があるか
- 戻る・取り消し・変更破棄・破壊的操作の扱いが適切か
- キーボードとフォーカス、ラベル、文字コントラスト、レスポンシブ対応に問題がないか
- 元仕様の全機能に到達でき、意図せず削除されていないか

重大なFAIL: 主タスクを開始／完了できない、機能が行方不明、重大なアクセシビリティ障害、誤認させる偽の操作。これらがある状態で「完成」と報告しない。
実機・ブラウザ未確認の項目は NOT TESTED とし、PASS と偽らない。

## レビューの方法

重要な画面改修では異なる3視点の批評を行い、1人の判定役で最終判断する。
- Critic 1: 初心者の認知負荷・最初の一手
- Critic 2: 実際の作業導線・機能到達性
- Critic 3: 視覚階層・可読性・アクセシビリティ
- Judge: 重要度 P0〜P3、採用する修正、残るトレードオフを確定

単純な修正には過剰なプロセスを課さない。指摘がある場合は、改善して再検査。大規模UIではこのサイクルを最大2周の目安で実施する。

## ユーザーへの報告形式

画面の狙い、主要タスクの到達方法、機能をどの階層に置いたか、ゲートのFAIL/NOT TESTEDを簡潔に述べる。
報告自体も冗長にしない。画面とレビューは別成果物にし、説明文をUIの中に過剰に埋め込まない。
