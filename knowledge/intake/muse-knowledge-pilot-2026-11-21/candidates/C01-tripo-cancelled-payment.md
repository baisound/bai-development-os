# 判断事例 C01：解約済みサービスの決済失敗は「問題」として扱わない

## Evidence（証拠）

| 項目 | 内容 |
|---|---|
| evidence class | DECLARED（オーナー本人の申告）＋ REAL（Gmail の決済失敗通知メールで観測） |
| observed_at | 2026-11-21 |
| scope | サブスクリプション監査（月次再チェック） |
| 事実 | Tripo AI は2026年11月にオーナーが解約済み。その後 ¥14,400 の決済失敗通知が届いたが、解約済みである以上、失敗は想定内で対応不要 |
| source | オーナー発言（2026-11-21）／ Gmail 決済失敗通知（2026-11-04） |

## 観察（何が起きたか）

- 初回のサブスク監査では、Tripo の決済失敗を「未払い・要対応」の問題として提示した。
- しかし実態は「解約済み → 請求が止まらず失敗しただけ」であり、問題として提示すること自体がノイズだった。
- 教訓： **決済失敗の通知だけでは問題と断定できない。解約・退会の状態を先に確認する。**

## Recommendation（推奨）

- サブスク監査・月次再チェックでは、各サービスについて「契約状態（継続中／解約済み／不明）」を先に持ち、決済失敗は継続中サービスのときだけ問題として提示する。
- 解約済みと確認できたサービスは、監査の設定（除外・状態メモ）に記録し、以後は失敗通知を報告対象から外す。

## Policy Candidate（候補）

| | 内容 |
|---|---|
| current | 決済失敗メールがあれば一律に「要対応」として提示 |
| proposed | 契約状態を確認し、解約済みの失敗は提示しない。状態不明の失敗のみ「確認が必要」として提示 |
| rationale | ノイズを減らし、本当の未払い（例： 請求アカウント停止に至ったケース）への注意を残すため |

## Safety Floor チェック

- 本候補は「提示の仕方」の変更であり、安全フロア（解約操作の事前承認ルール等）には触れない。
- 解約そのものを自動実行する話ではない。解約は従来どおり、サービスごとにオーナーのその場の明示承認が必要。
