## 1. 未解決（UNRESOLVED）の重大Issue詳細

### 【CRIT-002】抽選結果と停止位置の整合性 (Severity: CRITICAL / Status: UNRESOLVED)

* **Problem**: 提示された計算式に**深刻な数理バグ**が存在し、0度基準や回転方向、物理的なポインター位置との整合性が全く取れていません。
* **Evidence (数理的検証)**:
  * Builder の提示した計算式：
    * `sectorAngle = 360 / N`
    * `pointerAngle = (sectorAngle * selectedIndex + sectorAngle / 2) % 360`
    * `targetAngle = pointerAngle + additionalRotations`
    * `finalRotation = targetAngle`
  * **検証：N = 4, sectorAngle = 90度, pointerAngle = (90 * selectedIndex + 45) % 360**
    * ※前提条件：Canvas描画の基準0度を右端（3時方向）、時計回りの回転を正、固定ポインターの位置を12時方向（270度方向）と定義します。
    * **ケース1：selectedIndex = 0**
      * `pointerAngle = 45` 度（セクター0の中央）
      * `targetAngle = 45 + 1800 (5回転) = 1845` 度
      * `finalRotation = 1845` 度
      * この角度で Canvas要素を回転（`rotate(1845deg)`）させると、1845 % 360 = **45度時計回り**に回転します。
      * 回転前、セクター0（45度方向）は右下（4:30方向）にあります。これを45度時計回りに回転させると、**90度方向（下、6:00方向）に移動**します。
      * 12時方向（ポインター位置）を指すのは、対向にあるセクター2（回転により180〜270度の範囲が12時位置に到達）になります。
      * **結果：当選は「セクター0」なのに、見た目は「セクター2」を指して停止（ズレ発生：不整合）**。
    * **ケース2：selectedIndex = 1**
      * `pointerAngle = (90 * 1 + 45) = 135` 度
      * `finalRotation = 135 + 1800 = 1935` 度（**135度時計回り**に回転）
      * 回転前、セクター1（135度方向）は左下（7:30方向）にあります。これを135度時計回りに回転させると、270度方向（上、12:00のポインター位置）にピッタリ重なります。
      * **結果：このケースのみ、たまたま12時位置に一致します**。
    * **ケース3：N = 6, selectedIndex = 5**
      * `sectorAngle = 60` 度
      * `pointerAngle = (60 * 5 + 30) = 330` 度
      * `finalRotation = 330 + 1800 = 2130` 度（**330度時計回り**に回転）
      * 回転前、セクター5（330度方向）は右上（1:30方向）にあります。これを330度時計回りに回転させると、330 + 330 = 660 ≡ **300度方向（10:00方向）に停止**します。
      * **結果：当選は「セクター5」なのに、12時位置を指さず、完全にズレて停止します**。
  * **分析**:
    Builderは、当選したセクターの角度（`pointerAngle`）を**そのままルーレット盤全体の回転角**として適用してしまっています。
    本来、特定の角度（`pointerAngle`）にあるセクターをポインター位置（`pointerPosition` = 12時方向 = 270度）まで移動させるために必要な回転角 $\theta$ は、
    $\theta = \text{pointerPosition} - \text{pointerAngle}$ （負の場合は +360）
    すなわち、
    `finalRotation = additionalRotations + (270 - pointerAngle)`
    でなければなりません。この数理的な整合性計算が全く欠落しているため、ルーレットとして機能しません。
* **Impact**: 表示される当選結果のテキストと、画面上のルーレット盤の停止位置（ポインターが指すエリア）が毎回ズレるため、アプリケーションとして根本的なバグとなります。
* **Recommended Fix**:
  0度基準、回転方向、ポインター位置の関係を正しく反映した、以下の整合性計算式（またはそれに準ずる数理モデル）を決定してください。
  ```javascript
  const sectorAngle = 360 / N;
  // 当選セクターの中央の角度（右端3時方向を0度として反時計回り/時計回り等、Canvasの座標系に合わせる）
  const targetSectorCenter = sectorAngle * selectedIndex + sectorAngle / 2;
  // 12時位置（270度）にそのセクターを移動させるための回転角
  // 時計回り回転の場合： (270 - targetSectorCenter + 360) % 360
  const stopAngle = (270 - targetSectorCenter + 360) % 360;
  // 累積回転角度に加算
  finalRotation = baseRotation + additionalRotations + stopAngle;
  ```

### 【CRIT-001 / CRIT-003】描画とアニメーション方式の致命的な混在 (Severity: HIGH / Status: UNRESOLVED)

* **Problem**: Canvas描画とCSS transitionアニメーションの2つのアプローチが、同一設計書内で**完全に矛盾したまま混在**しています。
* **Evidence**:
  * **セクション2**: 「ルーレット全体の回転は、**Canvas内部をrequestAnimationFrameで制御**」
  * **セクション7**: 「**CSS transformを使用し、transform: rotate(...)などで回転。transitionとtransitionendを適切に使用**」
* **Impact**: 
  * Canvasのコンテキスト（`ctx.rotate`）を `requestAnimationFrame` で回す場合、CSSの `transform: rotate` や `transition` は不要であり、CSSのイージング設定も効きません。
  * Canvas要素そのものをCSS transitionで回す場合、Canvas内部を毎フレームクリアして再描画する必要はありません。
  * この2つを混在して実装しようとすると、アニメーション制御や角度の同期、回転終了判定（`transitionend`）が競合し、描画バグや著しいパフォーマンス劣化、コードの崩壊を招きます。
* **Recommended Fix**: 
  * 小規模フロントエンドとして最もシンプルで保守性の高い**「Canvasには静止したルーレットを1度だけ描画し、回転自体はCanvas要素全体をCSS transition（`transform: rotate(...)`）で回転させる」方式**に決定し、統一してください。セクション2から `requestAnimationFrame` の記述を完全に排除する必要があります。

* **Problem**: 最低候補数等の制限値は設定されましたが、**詳細設計が完全にプレースホルダーで放置されています**。

* **Impact**: 空白行の処理方法や重複候補の処理、最大制限超過時の処理が未決定のまま実装フェーズに移行すると、実装者の自己解釈によって挙動がブレたりバグが生じるリスクが残ります。
